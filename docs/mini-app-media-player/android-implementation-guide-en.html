Mini App Media Player — Android Implementation Guide

Architecture and engineering rules for connecting media played by a Telegram Mini App WebView to Android MediaSession, a foreground notification, the in-app media bar, and minimized Mini App tabs.

ArchitectureBridgeLifecycleSecurityBatteryTesting

1. Goals and boundaries

  • Expose Play/Pause and Seek outside the WebView through Android media controls.
  • Keep audio playback owned by the web page. Native code mirrors state and sends control requests; it does not decode or play the Mini App audio.
  • Preserve playback and controls when the Mini App is minimized or Telegram is in the background.
  • Avoid polling and repeated notification/artwork updates.
  • Keep the generic WebApp bridge detached after minimization; only the allowlisted media messages remain available.
Single active player: Android exposes one active Mini App media session. When another Mini App starts playing, the previous session receives a Pause request and loses active MediaSession status.

Android → Web event

media_playback_control_requested contains either {is_playing} or {seek_to}. JavaScript applies the request to the actual media element and reports the settled state back.

Seek rule: never echo audio.currentTime immediately after assigning a new seek target. Native enters loading state and waits for seeked/playing; this prevents stale pre-seek positions from snapping the scrubber backwards.

4. Lifecycle

Visible sheet

The complete WebApp bridge is attached. Media events update the in-sheet bar, MediaSession, notification, and any existing tab snapshot.

Minimized to a tab

The WebView is preserved only when active media exists. The ordinary bridge is detached and visibility_changed(false) is delivered. A restricted media delegate accepts only the four allowlisted media events. Audio remains owned by the WebView.

Restored

The WebView and callback are rebound, visibility_changed(true) is delivered, and one full playback snapshot resynchronizes Native and Web state.

Full close

The MediaSession is released, the notification/service is stopped, artwork loading is cancelled, and the WebView is destroyed.

Renderer crash

onRenderProcessGone clears media metadata immediately so stale controls and an orphan notification cannot survive a dead renderer.

Long pause

After 30 minutes continuously paused, the foreground service and notification are suspended. Metadata is retained in memory, so a later Play event can reactivate the session without requiring the page to resend track metadata.

5. Security and input validation

  • WebMessage events are accepted only from the main frame.
  • The message source origin must equal the current top-level document origin.
  • After minimization, only media event names are allowlisted; all other WebApp APIs remain detached.
  • Maximum media payload size is 16 KiB.
  • Title and artist are trimmed and limited to 256 characters.
  • Cover URLs are limited to 2,048 characters and must have an HTTP(S) scheme and a host.
  • Position and duration must be finite, non-negative, and no greater than 5 hours.
  • Playback rate must be finite and between 0.1× and 16×.
  • Validation is performed in Native code even when the JavaScript SDK already validates the value. Web content can bypass SDK helpers.
  • PendingIntents are immutable, the service and receiver are not exported, and receiver intents address an explicit component and session key.

6. Battery and performance rules

  • Background operation is event-driven. Do not send position once per second while minimized or when document.hidden is true.
  • Native estimates position using the last position, SystemClock.elapsedRealtime(), and playback rate.
  • The SDK coalesces accidental position-only background messages and flushes one snapshot after activation.
  • Android MediaSession receives position and speed, allowing the system to animate progress without notification reposts.
  • Notification content is reposted only when title, artist, artwork, playing, loading, or controllability changes.
  • Media metadata and album-art bitmap are sent to MediaSession only when their values change.
  • Minimized-tab time redraws and loading animation run only while their parent window is attached and visible.
  • Artwork uses the image loader/cache and requests a bounded display size. Do not submit a new cover URL on every progress event.
  • No additional WakeLock is acquired by this feature.

7. Android platform integration

  • The manifest declares FOREGROUND_SERVICE_MEDIA_PLAYBACK and registers BotWebViewMediaService with foregroundServiceType="mediaPlayback".
  • The service uses the existing Telegram notification channel and starts with startForegroundService/startForeground.
  • PlaybackStateCompat publishes Play, Pause, Play/Pause and Seek actions when controls are available. Loading or disconnected state temporarily disables unsafe transport actions.
  • A loading timeout prevents controls from remaining permanently stuck when a Mini App fails to acknowledge a request.
  • A pending-seek guard ignores stale position messages until the reported position reaches the target or the safety timeout expires.

9. Maintenance checklist

  • Keep media event parsing centralized; normal and preserved bridges must use identical validation.
  • Do not turn the preserved bridge back into a general-purpose WebApp bridge.
  • Do not call release() when minimizing; call it only for a full close.
  • Do not rebuild notifications or resend artwork for progress-only changes.
  • Any new media field needs validation, snapshot persistence, restore behavior, and background semantics.
  • When changing WebView lifecycle code, retest notification controls while the sheet is minimized.
