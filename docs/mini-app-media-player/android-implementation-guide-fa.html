راهنمای پیاده‌سازی اندروید پخش‌کنندهٔ Mini App

معماری و قواعد فنی اتصال رسانهٔ در حال پخش داخل WebView مینی‌اپ به MediaSession اندروید، نوتیفیکیشن foreground، نوار پخش داخل برنامه و Tab کوچک‌شدهٔ Mini App.

معماریBridgeچرخهٔ حیاتامنیتباتریتست

۱. هدف‌ها و مرزهای طراحی

  • فراهم‌کردن Play/Pause و Seek خارج از WebView از طریق کنترل‌های رسانه‌ای اندروید.
  • مالک پخش واقعی همچنان صفحهٔ وب است. کد Native فقط وضعیت را منعکس می‌کند و درخواست کنترل می‌فرستد؛ فایل صوتی Mini App را decode یا پخش نمی‌کند.
  • ادامهٔ پخش و کنترل هنگام Minimize شدن Mini App یا رفتن تلگرام به پس‌زمینه.
  • جلوگیری از polling و به‌روزرسانی تکراری نوتیفیکیشن یا artwork.
  • پس از Minimize، Bridge عمومی WebApp قطع می‌ماند و فقط پیام‌های مجاز رسانه عبور می‌کنند.
فقط یک Player فعال: اندروید فقط یک MediaSession فعال برای Mini Appها ارائه می‌کند. با شروع پخش در Mini App دیگر، برای session قبلی درخواست Pause ارسال شده و وضعیت فعال MediaSession از آن گرفته می‌شود.

۴. چرخهٔ حیات

Sheet قابل‌مشاهده

Bridge کامل WebApp متصل است. eventهای رسانه، Media Bar، MediaSession، نوتیفیکیشن و snapshot احتمالی Tab را به‌روز می‌کنند.

Minimize به Tab

WebView فقط در صورت وجود رسانهٔ فعال حفظ می‌شود. Bridge عمومی قطع و visibility_changed(false) ارسال می‌شود. delegate محدود فقط چهار event مجاز رسانه را دریافت می‌کند و صوت همچنان متعلق به WebView است.

بازگشت به Sheet

WebView و callback دوباره متصل، visibility_changed(true) ارسال و یک snapshot کامل برای همگام‌سازی Web و Native فرستاده می‌شود.

بستن کامل

MediaSession آزاد، سرویس و نوتیفیکیشن متوقف، بارگیری کاور لغو و WebView نابود می‌شود.

Crash شدن renderer

onRenderProcessGone فوراً metadata را پاک می‌کند تا کنترل قدیمی یا نوتیفیکیشن یتیم باقی نماند.

Pause طولانی

بعد از ۳۰ دقیقه Pause پیوسته، foreground service و نوتیفیکیشن suspend می‌شوند. metadata در حافظه حفظ می‌شود تا Play بعدی بدون ارسال دوبارهٔ اطلاعات Track، session را فعال کند.

۵. امنیت و اعتبارسنجی ورودی

  • پیام WebMessage فقط از main frame پذیرفته می‌شود.
  • origin فرستنده باید دقیقاً با origin سند top-level فعلی یکسان باشد.
  • بعد از Minimize فقط نام eventهای رسانه در allowlist هستند و سایر APIهای WebApp قطع می‌مانند.
  • حداکثر اندازهٔ payload رسانه ۱۶ KiB است.
  • عنوان و خواننده trim شده و حداکثر ۲۵۶ کاراکتر هستند.
  • URL کاور حداکثر ۲۰۴۸ کاراکتر، دارای host و فقط با scheme نوع HTTP(S) است.
  • position و duration باید finite، نامنفی و حداکثر ۵ ساعت باشند.
  • playback rate باید finite و بین ۰٫۱ تا ۱۶ باشد.
  • اعتبارسنجی در Native هم انجام می‌شود؛ چون محتوای وب می‌تواند helperهای SDK را دور بزند.
  • PendingIntentها immutable هستند، service و receiver export نشده‌اند و Intent کنترل، component صریح و کلید session دارد.

۶. قواعد مصرف باتری و کارایی

  • عملیات پس‌زمینه event-driven است. در حالت Minimize یا وقتی document.hidden است، position هر ثانیه ارسال نشود.
  • Native زمان را با آخرین position، مقدار SystemClock.elapsedRealtime() و playback rate محاسبه می‌کند.
  • SDK پیام‌های position-only اشتباهی در پس‌زمینه را تجمیع و پس از فعال‌شدن فقط یک snapshot ارسال می‌کند.
  • MediaSession position و speed را دریافت می‌کند تا خود سیستم progress را بدون repost نوتیفیکیشن حرکت دهد.
  • نوتیفیکیشن فقط با تغییر title، artist، artwork، playing، loading یا controllability دوباره ساخته می‌شود.
  • metadata و bitmap کاور فقط هنگام تغییر واقعی به MediaSession ارسال می‌شوند.
  • redraw زمان Tab و animation مربوط به loading فقط وقتی parent window متصل و قابل‌مشاهده است اجرا می‌شوند.
  • کاور از ImageLoader و cache استفاده می‌کند و با اندازهٔ نمایشی محدود درخواست می‌شود. URL کاور نباید با هر progress تغییر کند.
  • این قابلیت WakeLock اضافه نمی‌گیرد.

۷. اتصال به امکانات اندروید

  • Manifest مجوز FOREGROUND_SERVICE_MEDIA_PLAYBACK را دارد و BotWebViewMediaService با foregroundServiceType="mediaPlayback" ثبت شده است.
  • سرویس از notification channel موجود تلگرام و الگوی startForegroundService/startForeground استفاده می‌کند.
  • PlaybackStateCompat هنگام قابل‌کنترل‌بودن، actionهای Play، Pause، Play/Pause و Seek را منتشر می‌کند. حالت loading یا قطع‌شدن Bridge موقتاً action ناامن را غیرفعال می‌کند.
  • timeout مربوط به loading مانع ماندن دائمی کنترل‌ها در spinner می‌شود اگر Mini App پاسخ ندهد.
  • محافظ pending-seek پیام position قدیمی را نادیده می‌گیرد تا target تأیید شود یا timeout ایمنی پایان یابد.

۹. چک‌لیست نگهداری

  • parse کردن eventهای رسانه متمرکز بماند؛ Bridge عادی و preserved باید دقیقاً یک اعتبارسنجی داشته باشند.
  • Bridge preserved دوباره به Bridge عمومی WebApp تبدیل نشود.
  • هنگام Minimize متد release() فراخوانی نشود؛ فقط Close کامل باید session را آزاد کند.
  • برای تغییر صرفاً position، نوتیفیکیشن یا artwork دوباره ساخته نشود.
  • هر فیلد جدید نیازمند validation، ذخیره در snapshot، رفتار restore و تعریف رفتار پس‌زمینه است.
  • پس از تغییر lifecycle WebView، کنترل نوتیفیکیشن در حالت Minimize دوباره تست شود.

این سند قابلیت سفارشی MediaPlayer در همین سورس اندروید را شرح می‌دهد و تا زمان پذیرش جداگانه، بخشی از API عمومی upstream تلگرام محسوب نمی‌شود.
